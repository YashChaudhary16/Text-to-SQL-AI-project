# How it works: a friendly tour

Read this **before** [architecture.md](architecture.md). It explains every part of the project in plain
language first, then connects each idea to the actual code. When you finish, you should be able to open any
file and know why it exists and who talks to it.

Every section follows the same pattern:

> 🧠 **In plain words**: the idea, with an everyday analogy
> 🔧 **In the code**: the file, the important functions, and what goes in and out

---

## 1. The 30-second version

A manager wants to know *"What were our top 5 product categories by revenue in 2002?"*. The answer is buried in
a database with 24 tables and 425 columns named things like `cs_ext_sales_price`. The manager doesn't know SQL
and shouldn't have to.

So we built a small **team of AI helpers**, each with one job, plus some non-AI machinery that keeps them
honest:

| Team member | Everyday analogy | What it really is |
|---|---|---|
| **Receptionist** | Listens to the request, asks "do you mean X or Y?" if it's unclear | The `understand` + `clarify` steps (an LLM) |
| **Librarian** | Knows which shelves (tables) hold the answer | The `retrieve` step (search code + the receptionist's hints) |
| **Analyst** | Writes the database query | The `write_sql` step (an LLM) |
| **Safety inspector** | Checks the query can't break anything before it runs | The SQL guard (plain Python, no AI) |
| **Database** | The filing cabinet with all the data | DuckDB, a fast analytics database in a file |
| **Spokesperson** | Explains the results in plain English | The `respond` step (an LLM) |
| **Manager of the team** | Decides who works next, remembers where we left off | LangGraph, the workflow engine |
| **Front desk window** | The website the user types into | The Next.js frontend |
| **Mail room** | Carries messages between the website and the team | The FastAPI backend API |

Two more things sit in the background:
- **The company handbook**, the *semantic layer*. A document that explains what every table and column means in
  business terms ("`net_paid` is what we call revenue"). Every AI helper reads from it.
- **The phone book of AI providers**, the *LLM router*. A list of which AI services to call and in what order,
  so if one is busy we automatically try the next.

## 3. Before anyone asks anything: preparing the data and the handbook

### 3.1 The data (TPC-DS)

🧠 **In plain words.** We needed a realistic, complicated company database to practise on. TPC-DS is a famous
fake retailer used by the database industry to benchmark systems. It has stores, a catalog business and a
website, plus customers, products, dates and so on. It's generated by a program, so we can make it any size.

🔧 **In the code.**
- Command: `uv run sqlagent generate-data --sf 1` → function `generate_data()` in `backend/src/sqlagent/cli.py`.
- It asks DuckDB to install its `tpcds` extension and run `CALL dsdgen(sf=1)`, which writes about 19.6M rows
  into `backend/data/tpcds_sf1.duckdb` in about 5 seconds.
- **DuckDB** is like SQLite (a whole database in one file) but built for analytics: summing millions of rows
  quickly.
- Details of every table: [data-dictionary.md](data-dictionary.md).

### 3.2 The handbook (semantic layer)

🧠 **In plain words.** If you gave a new employee this database, they'd be lost: what is `ss_net_paid`? Is
revenue before or after coupons? What does "last year" mean when the data stops in 2003? Humans learn this from
colleagues; our AI learns it from a handbook. We wrote the handbook once, carefully, and every AI helper reads
the parts it needs.

🔧 **In the code.** There are three pieces:

1. **`backend/semantic/tpcds.yaml`**, written by hand. It holds:
   - plain-English descriptions of each table, with synonyms ("online sales" = `web_sales`)
   - meanings for columns, with shared patterns so we don't repeat ourselves (every `*_net_paid` column gets
     the same "revenue" explanation)
   - **dimension_keys:** a rule saying "a column ending in `item_sk` connects to the `item` table". The
     database doesn't record these connections, so we teach them.
   - **metrics**, e.g. `revenue = SUM(net_paid)`
   - **rules**, e.g. "to total all channels, add each channel separately, never join them together"
2. **`backend/src/sqlagent/semantic/builder.py`**, run with `uv run sqlagent build-catalog`. It reads the
   YAML, then **looks at the actual database** to add facts a human shouldn't type by hand:
   - each column's type and each table's row count
   - the complete list of values for small columns (e.g. education is exactly one of `'Primary'`,
     `'College'`, `'4 yr Degree'`, …), so the AI spells filters correctly
   - the date range each sales table covers, so "last year" means 2002

   It saves everything as **`backend/semantic/tpcds.catalog.json`**.
3. **`backend/src/sqlagent/semantic/catalog.py`** loads that JSON when the server starts and has two
   "printing" functions that turn it into text for the AI:
   - `render_overview()`: one line per table (short), used by the receptionist.
   - `render_tables([...])`: full detail for a few chosen tables, used by the analyst.

> 💡 Why build a JSON file instead of reading the database at startup? Reading the database costs time, and on
> the hosted version it costs free-tier compute. The JSON is computed once and committed to git.

The same catalog also generates the column reference in `docs/data-dictionary.md` (`uv run sqlagent docs`), so
the documentation and the AI's knowledge always match.

## 4. Following one question from start to finish

Let's trace a real run (captured during testing with the local `gpt-oss:20b` model):

> **"What were the top 5 product categories by revenue in 2002?"**

### Step 0: The website sends the question

🧠 You type and press **Ask**. The website sends the question to the backend and keeps the connection open, so
the backend can send back a series of small updates ("I understood it…", "I found these tables…") instead of
one big reply at the end.

🔧
- `frontend/src/components/App.tsx`: the page. Pressing Ask calls `send()` from `useChat`.
- `frontend/src/lib/useChat.ts`: keeps the list of *runs* (one run = one question and everything that happened
  to it). It creates a new run and calls `streamChat()`.
- `frontend/src/lib/api.ts` → `streamChat()` does `POST http://localhost:8000/api/chat` with
  `{"message": "...", "thread_id": ...}` and reads the reply as a **stream of events**.
- This streaming format is **SSE (Server-Sent Events)**: plain text chunks like
  `event: step` / `data: {...}`. The browser's built-in `EventSource` can only do GET requests, so we wrote a
  tiny parser ourselves (`parseBlock()`).

### Step 1: The mail room receives it

🧠 The backend checks the basics: is this visitor sending too many questions? Did they include their own Claude
key, and does it look valid? Is this a brand-new question, or the answer to a question we asked them earlier?

🔧 `backend/src/sqlagent/api/app.py` → `chat()`:
1. If the `X-Anthropic-Key` header is present, check it starts with `sk-ant-`. Otherwise apply the per-IP rate
   limit (`_check_rate_limit`).
2. Pick a `thread_id` (one per conversation; a new random ID if the website didn't send one).
3. `graph.aget_state(...)` asks "is this conversation paused waiting for the user?". If yes, the message is an
   answer and we **resume**; if no, we start a **new turn** with `new_turn(message)`.
4. Return `EventSourceResponse(_stream(...))`. `_stream` runs the workflow and turns each step into an SSE event
   (`_events_for()`).

At startup, `lifespan()` builds everything once: loads the catalog, opens the database, creates the LLM router
and builds the graph.

### Step 2: The receptionist understands the request (`understand`)

🧠 An AI reads the question along with a one-page summary of the warehouse, and fills in a form:
- What kind of request is this: a data question, a question *about* the data, or off-topic?
- Rewrite it as a complete, standalone sentence. This matters for follow-ups like "now by month".
- Which tables will we probably need?
- What reasonable assumptions am I making? (No channel mentioned → all channels combined.)
- Is this too vague to answer? If so, what should I ask?

In our run it filled in: *data question; tables: store, catalog and web sales, item, date_dim; assumption:
all channels combined.*

🔧 `backend/src/sqlagent/graph/agent.py` → `SQLAgent.understand()`:
- **System prompt:** `UNDERSTAND_SYSTEM` in `graph/prompts.py` plus `catalog.render_overview()`.
- **User message:** the question, the last 3 Q&As (for follow-ups) and any clarifications so far.
- **The "form"** is the Pydantic model `Understanding` in `graph/state.py`. We ask the LLM to reply in exactly
  that JSON shape (*structured output*), so the code gets clean fields, not prose.
- **Safety net:** small models sometimes write SQL into the "standalone question" field. If it starts with
  `SELECT`/`WITH`, we fall back to the user's original text (`SQL_START` regex).
- If it needs clarification (and we haven't already asked twice), it stores `pending_clarification`.

### Step 3 (sometimes): The receptionist asks you something (`clarify`)

Our example didn't need this; §5 walks through a question that does.

### Step 4: The librarian finds the right shelves (`retrieve`)

🧠 The analyst works better with a short, relevant reading list than with the entire 425-column handbook. The
librarian combines three things:

1. **The receptionist's suggestions**, which are good at meaning ("online" means `web_sales`).
2. **A keyword search** over every table and column description, which is good at details ("TV" matches the
   `p_channel_tv` column in `promotion`). A keyword hit only counts if it's strong *and* connects directly to a
   suggested table, so random matches don't sneak in.
3. **A road map of connections.** If two chosen tables can't connect directly, add the table in between. For
   example, `store_sales` → `household_demographics` → `income_band`. The calendar table is never used as a
   shortcut between unrelated tables, because it connects to almost everything.

🔧 `backend/src/sqlagent/retrieval.py` → `SchemaRetriever.retrieve(question, linked_tables)`:
- **The keyword search is BM25**, a classic search-engine ranking formula (the `rank-bm25` library).
  `tokenize()` lowercases, splits `snake_case` and trims plurals. Every table and column becomes a small
  "document" to search.
- **The road map** comes from `catalog.neighbors` (built from the FK rules in the YAML). `_shortest_path()` is a
  breadth-first search, skipping `date_dim`/`time_dim` (`BRIDGE_EXCLUDED`).
- **Output:** the list of table names stored in `state["tables"]`.

### Step 5: The analyst writes the SQL (`write_sql`)

🧠 A (usually stronger) AI gets the question, the assumptions, and the detailed handbook pages for just those 5
tables, including the exact meaning of each column, how tables connect, the metric definitions and the rules.
It writes one database query.

🔧 `SQLAgent.write_sql()`:
- The prompt is `SQL_SYSTEM` + `catalog.render_tables(state["tables"])`.
- The reply follows the `SQLDraft` form: a short `plan` plus the `sql`.
- If this is a retry, the prompt also includes the failed SQL and the error message (`SQL_RETRY`).
- From the third attempt on, it sets `escalate=True`, which tells the LLM router to try Claude first if a Claude
  key is available.

### Step 6: The safety inspector checks it, then the database runs it (`execute`)

🧠 AI-written code is never trusted blindly. Before running, a checker reads the query's *structure* (not just
its text) and refuses anything that isn't a single read-only question about our known tables: no deleting, no
reading files, no peeking at other databases. It also caps how many rows can come back. Then the database runs
it, with a stopwatch: if it takes longer than 20 seconds, we pull the plug.

Even if the inspector somehow missed something, the database itself is opened in **read-only, no
outside access** mode. That's two locks on the same door.

In our real run, the **first attempt failed** (the AI referred to a table nickname `i` that it never defined).
The error went back to the analyst, the **second attempt worked**, and 5 rows came back in 373 ms.

🔧
- **`backend/src/sqlagent/db/guard.py` → `guard_sql()`** uses **sqlglot**, a SQL parser, to turn the query into
  a tree and walk it:
  - exactly one statement, and it must be a query
  - no forbidden node types (`FORBIDDEN_NODES`) or functions (`read_csv`, `getenv`, …)
  - only allowed table names (CTE names excepted)
  - adds or caps `LIMIT` at `max_result_rows + 1`; the +1 lets us detect "there were more rows"
- **`backend/src/sqlagent/db/warehouse.py` → `Warehouse.run()`**:
  - the connection is opened with `read_only=True`, `enable_external_access=False` and
    `lock_configuration=True`
  - a `threading.Timer` calls `cursor.interrupt()` on timeout
  - results are converted to JSON-friendly values (`_jsonable`)
- **`SQLAgent.execute()`** catches errors and records them, then `route_after_execute()` decides: success →
  `respond`; failure with attempts left → back to `write_sql`; out of attempts → `give_up`.

### Step 7: The spokesperson explains the result (`respond`)

🧠 An AI reads the question, the SQL, and the first 30 rows of results, and writes a short plain-English answer
with the key numbers, listing the assumptions it made. In our run (lightly condensed):

> The top five product categories by revenue in 2002 were Music ($194,490,482.39), Electronics, Home, Shoes and
> Women. These totals combine sales from the store, catalog, and web channels.

We checked these numbers against a hand-written query and they match exactly.

🔧 `SQLAgent.respond()` uses `RESPOND_SYSTEM` / `RESPOND_USER` prompts with a CSV preview of the rows. `_finish()`
saves the answer and adds this Q&A to `history`, so the next question can say "now break that down by month".

### Step 8: The website shows everything live

🧠 While all this happens, the website shows a growing checklist ("Understood the request ✓", "Found 5 tables
✓", "Attempt 1 failed, retrying…", "Ran the query ✓"), and finally the SQL, the table and the answer.

🔧 Each backend step becomes an SSE event, which `useChat` turns into an update of the current run:

| Backend event | What the website does | Component |
|---|---|---|
| `thread` | remembers the conversation ID | `useChat` |
| `step` | adds a line to the timeline | `AgentTrace.tsx` |
| `clarification` | shows the question and option buttons | `RunView.tsx` |
| `result` | shows the SQL and the table | `SqlBlock.tsx`, `ResultTable.tsx` |
| `answer` | shows the explanation and token count | `RunView.tsx`, `AgentTrace.tsx` |
| `error` | shows a red message | `RunView.tsx` |
| `done` | marks the run finished | `useChat` |

## 5. The clarification detour: how the system "pauses and waits"

Ask **"Who are our best customers?"** and the receptionist realises "best" could mean most revenue, most orders
or most profit. These give different answers, so it asks.

🧠 **The tricky part.** The web works in separate request/response exchanges. The first request ends when we ask
the question. Minutes later, a *new* request arrives with "Highest net revenue". How does the team remember
where it was?

**The "save game" analogy:** after every step, LangGraph saves the full state of the conversation, like a save
point in a video game. When the AI needs to ask the user something, it calls `interrupt()`, which means "save
here and stop". When the answer arrives, we load the save and **continue from that exact spot**, with the
answer filled in.

```
Request 1:  understand → clarify ──interrupt()──► 💾 saved; website shows the question + buttons
                                                  (request ends)
Request 2:  user clicks "Highest net revenue"
            API sees the thread is paused → Command(resume="Highest net revenue")
            💾 loaded → clarify finishes → understand again (now with the answer) → retrieve → …
```

🔧
- **`SQLAgent.clarify()`** calls `interrupt({...question, options...})`. On resume, the same function receives
  the user's answer as the return value of `interrupt()` and appends it to `state["clarifications"]`.
- **The "save game" storage is the checkpointer:**
  - **locally:** `InMemorySaver` (lost when the server restarts)
  - **in production:** `AsyncPostgresSaver` (a Postgres database such as Neon), chosen in `lifespan()` based
    on `DATABASE_URL`
- **In the API**, `chat()` checks `snapshot.interrupts` to decide between resume and new turn.
- **In the website**, a run in status `"waiting"` shows option buttons; clicking one (or typing) calls `send()`,
  which continues the same run instead of starting a new one.
- **The receptionist can't ask forever:** after `max_clarifications` (2), it's told to use defaults.

In the live test, after "Highest net revenue" it returned the top 20 customers and correctly used the "bill to"
customer for catalog and web orders, a rule it learned from the handbook.

## 6. When things go wrong

| Problem | What happens | Where |
|---|---|---|
| The SQL has an error | Error message goes back to the analyst; up to 3 attempts | `route_after_execute()` |
| Still failing after 3 tries | Polite "couldn't do it, try rephrasing" message | `give_up()` |
| The AI writes something dangerous (`DROP TABLE`) | Guard refuses; it counts as a failed attempt; nothing runs | `guard.py` |
| The query is too slow | Stopped after 20 s; "add filters" message to the analyst | `warehouse.py` |
| An AI provider is busy or out of free quota | Silently try the next provider in the list | `llm.py` |
| *All* providers fail | Friendly error event; details only in server logs | `_stream()` in `app.py` |
| Off-topic question ("weather?") | Fixed reply with example questions; no SQL, no LLM cost | `out_of_scope()` |

## 7. The phone book of AI providers (LLM router)

🧠 We don't want the code to say "always call Groq". Providers have outages, rate limits and costs. So each step
asks for a **role** ("I need the cheap router model" or "I need the SQL model"), and the router picks who
actually answers, trying them in order:

```
Normal visitor:            Groq (free) → Cerebras (free) → Ollama on your PC (free)
Visitor added Claude key:  Claude (their key, their bill) → then the free ones
SQL failing repeatedly:    Claude first, but only if some Claude key exists
Owner enabled own key:     free ones first → your Claude key as the last resort
```

Providers with no key configured are skipped automatically. With only Ollama configured, as on your machine
right now, the list is just `ollama:gpt-oss:20b`.

🔧 `backend/src/sqlagent/llm.py` → `LLMRouter`:
- **`structured(role, schema, messages)`** for form-shaped answers; **`text(role, messages)`** for prose.
- **`_candidates()`** builds the ordered list; `_build()` creates the right LangChain client: `ChatGroq`,
  `ChatOpenAI` (for Cerebras/OpenRouter, which speak OpenAI's format), `ChatOllama`, `ChatAnthropic`.
- **`_run()`** is the try-the-next-one loop. Every success returns a `CallRecord`: which model answered, which
  ones failed first, and how many tokens were used. The website shows this, and the future evaluation will use
  it to compute cost.
- **Configuration** (`backend/.env`, see `.env.example`): `ROUTER_MODELS`, `SQL_MODELS`, `GROQ_API_KEY`,
  `OLLAMA_BASE_URL`, …

> 🔐 **Visitor keys are never saved.** LangGraph's save-game feature copies some settings into the database, so
> a visitor's Claude key travels in a separate, never-saved "context" (`RunContext` in `graph/state.py`). In the
> browser, it lives only in that tab's `sessionStorage` (`frontend/src/lib/keyStore.ts`).

## 8. LangGraph, demystified

LangGraph is the "team manager". Three ideas cover 90% of it:

1. **State:** one shared notebook (a Python dict) that every step reads and writes. Ours is `AgentState` in
   `graph/state.py`: `question`, `tables`, `sql`, `result`, `answer`, `history`, … A step returns *only the
   fields it changed*, and LangGraph merges them in.
2. **Nodes:** the steps. Each one is a function `(state) -> changes`. Ours are methods on `SQLAgent`.
3. **Edges:** who goes next. Fixed edges (`write_sql` → `execute`) or conditional ones decided by a small
   function (`route_after_understand`, `route_after_retrieve`, `route_after_execute`).

Plus two extras we use:
- **Checkpointer:** the "save game" (§5).
- **`interrupt()` / `Command(resume=...)`:** pause and continue (§5).

All of this is wired together in **`build_graph()`** at the bottom of `graph/agent.py`. It's about 20 lines and
the best single place to see the whole workflow.

## 10. How we know it works (tests)

🧠 Testing with a real AI is slow, costs money, and gives slightly different answers each time. So the tests use
a **fake AI** (`ScriptedLLM` in `backend/tests/conftest.py`) that returns pre-written answers, while
everything else (the graph, the guard, the **real database**, the API) is real. That tests our machinery
precisely. Whether the *AI* is good is a different question, which the future evaluation harness will measure.

🔧 Run `cd backend && uv run pytest -q` (52 tests, about 2 seconds):

| File | Checks |
|---|---|
| `test_guard.py` | 19 kinds of dangerous SQL are refused; normal queries pass |
| `test_warehouse.py` | the database itself refuses writes and file access, even bypassing the guard |
| `test_retrieval.py` | the librarian picks sensible tables and connections |
| `test_llm.py` | the provider order is right; fallbacks and token counting work |
| `test_graph.py` | whole journeys: normal, clarification pause/resume, retry after error, unsafe SQL, off-topic, follow-ups |
| `test_api.py` | the event stream, clarification over two HTTP requests, rate limits, key validation |
| `test_docs.py` | the data dictionary covers every column |

## 11. Jargon cheat sheet

| Term | Meaning here |
|---|---|
| **LLM** | Large language model: the AI (gpt-oss, Claude, …) |
| **Open-weight / open-source model** | A model anyone can download and run (gpt-oss, Llama, Qwen); free through Groq's free tier or Ollama |
| **Groq / Cerebras / OpenRouter** | Companies that host open models behind an API |
| **Ollama** | A program that runs open models on your own computer (`localhost:11434`) |
| **Prompt / system prompt** | The instructions plus context we send the AI; ours are in `graph/prompts.py` |
| **Structured output** | Asking the AI to reply in an exact JSON shape (`Understanding`, `SQLDraft`) |
| **Token** | A chunk of text (~¾ of a word); providers count and limit usage in tokens |
| **Schema** | The structure of the database: tables, columns, types |
| **Fact / dimension table** | Facts are events with numbers (sales); dimensions describe them (products, dates) |
| **`_sk` / surrogate key** | An ID number used only to connect tables |
| **Join** | Combining two tables by matching keys |
| **Semantic layer** | Our handbook that maps business words to database columns |
| **Schema linking / retrieval** | Choosing which tables are relevant to a question |
| **BM25** | A classic keyword-ranking formula used by search engines |
| **sqlglot** | A library that parses SQL into a tree we can inspect |
| **DuckDB** | A fast single-file analytics database; **MotherDuck** is its cloud version |
| **LangChain** | A library of uniform wrappers around many AI providers |
| **LangGraph** | A library for building step-by-step AI workflows with state, branching, pause/resume |
| **Node / edge** | A step in the workflow / the arrow to the next step |
| **Checkpointer** | Where LangGraph saves conversation state between steps and requests |
| **Interrupt / resume** | Pause the workflow to ask the user, then continue from the same spot |
| **FastAPI** | The Python web framework for our backend |
| **SSE** | Server-Sent Events: the server pushes a stream of small messages over one HTTP response |
| **CORS** | The browser rule that lets the site on `:3000` talk to the API on `:8000` (`CORSMiddleware`) |
| **BYO key** | Bring Your Own key: a visitor's own Claude API key |
| **Rate limit** | Max requests per minute per visitor |

## 12. Where to start reading the code

A reading order that builds understanding step by step:

1. `backend/src/sqlagent/graph/agent.py`: read `build_graph()` at the bottom first (the whole workflow), then
   each node.
2. `backend/src/sqlagent/graph/state.py`: the notebook (`AgentState`) and the AI "forms".
3. `backend/src/sqlagent/graph/prompts.py`: what we actually tell the AI.
4. `backend/semantic/tpcds.yaml`: the handbook. Skim it, it's very readable.
5. `backend/src/sqlagent/retrieval.py` → `db/guard.py` → `db/warehouse.py` → `llm.py`.
6. `backend/src/sqlagent/api/app.py`: how it's exposed to the web.
7. `frontend/src/lib/useChat.ts` → `components/App.tsx` → `RunView.tsx` → `AgentTrace.tsx`.

### "I want to change…": quick lookup

| I want to… | Edit | Then |
|---|---|---|
| Teach the AI a new business term or fix a column meaning | `backend/semantic/tpcds.yaml` | `uv run sqlagent build-catalog && uv run sqlagent docs` |
| Change how the AI behaves (tone, rules, when to clarify) | `backend/src/sqlagent/graph/prompts.py` | test with `uv run sqlagent ask "..."` |
| Add a field the AI must fill in | the model in `graph/state.py` + where it's used in `agent.py` | add a test in `tests/test_graph.py` |
| Add a new workflow step | a method on `SQLAgent` + wire it in `build_graph()` | stream it in `api/app.py` `_events_for()`, show it in `AgentTrace.tsx` |
| Use different AI models | `backend/.env` (`ROUTER_MODELS`, `SQL_MODELS`, keys) | restart the server |
| Allow or block a SQL feature | `backend/src/sqlagent/db/guard.py` | add a case to `tests/test_guard.py` |
| Change limits (rows, timeout, retries) | `backend/src/sqlagent/config.py` or `.env` | — |
| Change what the website shows | `frontend/src/components/*` | `npx tsc --noEmit && npm run lint` |
